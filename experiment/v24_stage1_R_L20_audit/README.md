## 一、第一阶段：本人动作能否映射到 R，精度多少

### 1.1 先明确“映射”在这里到底做了什么

当前第一阶段没有任何跨尺寸适配算法，它就是最简参考实现 ①：

```text
theta_R(t) = theta_i(t)        # 45 维姿态参数原样搬运
beta_R  = 0（固定）            # R 的形状永远是标准 MANO
腕部位置锚定到 R 的参考锚点
```

因此**姿态参数迁移误差恒为 0**（`pose_parameter_transfer_error_rad = 0.0`）。下面所有残差都不是“算法误差”，而是**人手 β_i 与 R 的 β_R=0 之间的形态差异**在作用。这一点必须在写论文时讲清楚，否则 1.15° 会被误读成一个映射方法的精度。

另外 R 比操作者大 35%：源掌长 104.5 mm，R 掌长 141.3 mm，比值 **1.352**。

- 不能证明 L20 可执行：本版没有求解任何 q。

## 三、R 和 L20 的关系到底体现在哪里

按当前代码事实拆成四层，从上到下逐层变弱：

**① 21 个语义点对应（唯一的数据连接）**
L20 的 21 点来自 `experiment/v5_MANO-R拟合/l20_landmarks21_v5.json`：由 URDF 零位 FK 得到关节框架点、腕部根点，以及五个末节 STL 的端盖面积加权指尖点，统一到 `hand_base_link`。语义顺序与 MANO 21 点一一对应（wrist、thumb CMC/MCP/IP/tip、四指 MCP/PIP/DIP/tip）。

**② 一个 7 自由度相似变换（唯一的几何连接）**
`scale = 1.49202`、固定旋转、固定平移，把标准 MANO 手放进 L20 根坐标系。拟合目标就是这 21 点的平方和距离，结果 RMSE 35.52 mm。**R 与 L20 的全部几何关系就是这 7 个数 + 21 个点对应。**

**③ 运动学结构只存在于下游（v15–v19 的 q 级）**
L20 的 22 link / 21 revolute / 5 mimic（四指 DIP = 0.8917×PIP，拇指 IP = 1.1619×MCP）/ 16 个独立 q / 限位，是第二阶段的求解空间，保存在 `r_l20_model.npz` 与 URDF 里。v15–v19 在这些 q 上做过合成动作优化，**但 v22/v23 的“本人动作→R”管线完全没有触碰这一层**，所以 R 上的动作目前还没有任何“L20 可执行性”保证。

**④ v18 的 `K_R^L20` 是一条并行支路，没有接进 v22/v23**
`scripts/build_target_conditioned_sequence_v18.py` 做的事才是“把动作装进 L20 结构”：直接采用 L20 零位骨长与骨方向，只把 MANO 每条骨从参考方向到当前方向的**相对旋转**迁移过去。这条支路才真正让骨架长成 L20 的比例。但它：
- 输入是 17 帧固定合成序列，不是本人 774 帧；
- 与 v12 R 的“自然表面”`S_R` 没有并成同一个对象；
- 没有和 v22 的 R 序列做过对比。

**一句话**：现在 R 和 L20 的关系是“**用 L20 的总尺寸放置了一只标准人手**”，不是“L20 的几何替身”。表面 `S_R` 是纯 MANO；功能骨架 `K_R` 在 v15 文档里定义为人体语义；真正带 L20 比例的 `K_R^L20` 只存在于 v18 支路。共享表示 `z_R` 至今没有任何实现。

## 四、结论与下一步

**结论**

1. 阶段一的“映射”目前是恒等姿态搬运，骨方向 RMSE 1.153°、指尖对归一化 MAE 0.0358，数值上是好的，但**这不是跨尺寸方法的精度**，而是“没做适配”的基线。
2. R 与 L20 在**指骨长度（平均差 11.3 mm / 19.4%）、掌宽（+53%）、掌长（−14%）三项都不一致**；只有总手长（−1.5%）和 21 点静态 RMSE 35.5 mm 的量级对得上。
3. R↔L20 的连接只有 21 点对应 + 7 自由度相似变换。这解释了为什么用户看到的是“一只放大的自己的手”，而不是 L20。
4. 但阶段一的功能后果是可量化的：R 做不出本人最紧的拇指—小指（5.6 → 15.7 mm）和拇食指捏合（17.8 → 27.0 mm）。

**按优先级排序的下一步（均为计划，未运行）**

- [ ] 先解决 v23 遗留的动作质量问题：用同步 RGB 视频核对拟合骨架，补逐关节解剖/扭转约束。**在源动作可信之前，任何 R 上的精度数字都只是“搬运保真度”。**
- [ ] 给阶段一加真正的跨尺寸项：至少做骨长比例重映射（把操作者的骨长比映射到 R 的骨长比），再与当前恒等搬运对照，报告任务对误差与绝对位置误差的变化。这是本课题“两阶段”里第一阶段该有的最小版本。
- [ ] 把 v18 的 `K_R^L20` 接进本人序列，形成“自然表面 S_R 用于显示 + L20 条件化骨架用于求解”的同一份 R，再用同一指标对照。
- [ ] 若要让 R 在比例上真的像 L20，需要 β 参与 21 点拟合。这不是新想法：v5 的 β+尺度+theta_ref 对照已到 RMSE 10.84 mm（本版 R 是 35.52 mm），v13 的有界 β 候选是 35.16 mm。当年选 `β=0` 是为了保“可辨认人手形状”，属于设计取舍；是否放弃需先写入 `brainstorm.md` 再决定。
- [ ] 上述完成后再谈 L20 q 的可达性与 u。

**边界**：本版所有数字都不能支持“已实现跨尺寸映射”“R 已忠实表示本人动作”“R 可被 L20 执行”中的任何一条。第一、二条被 v23 的动作质量反馈否定，第三条从未运行。

## 五、附录：本人手指关节比例 vs L20 的 mimic 比例（2026-10-24 追加）

为设计“全驱动 R → 欠驱动 L20”的耦合处理，先量化 L20 硬编码的 mimic 比例与本人实际关节比例差多少。脚本 `scripts/measure_human_joint_ratio_v24.py`，输出 [human_joint_ratio.json](human_joint_ratio.json)。角度定义：相邻骨段方向的夹角（只含方向信息，不是量角器读数，仍受 v23 已记录的轴向扭转污染）。仅统计 PIP 屈曲 ≥ 11.5°（0.2 rad）的帧。

| 手指 | PIP 中位 | DIP 中位 | DIP/(PIP+DIP) 中位 | 有效帧 |
|---|---|---|---|---|
| 食指 | 28.2° | 33.1° | **0.525** | 753 |
| 中指 | 31.4° | **2.9°** | **0.084** | 774 |
| 无名指 | 18.9° | 10.6° | 0.355 | 770 |
| 小指 | 30.4° | 16.5° | 0.349 | 699 |
| 拇指 | MCP 15.5° | IP 22.2° | IP/MCP **1.545** | 108 |

L20 的四指 mimic 强制 **DIP/(PIP+DIP) 恒等于 0.8917/1.8917 = 0.4714**，拇指强制 IP = 1.1619×MCP。

两点结论：

1. **mimic 比例与本人手不符**：四指被固定在 0.471，本人实测在 0.084–0.525 之间。单看这一点就说明“角度直搬”必然系统性错位——即使源角度完全正确。
2. **但本人实测的分布本身不可信**：中指 DIP 中位只有 2.9°，而食指 DIP 比 PIP 还大（33.1° vs 28.2°）。人体 DIP 通常承担约 0.4 的段间屈曲，四个手指不可能差 6 倍。这是源拟合的非解剖关节分配的第二个症状（第一个是 v23 记录的 DIP 轴向扭转 64.69/62.17/72.81°），中指最严重。

**对方法设计的直接后果**：在源动作可信之前，**不要**用“匹配关节角”或“匹配每个关节的屈曲份额”作为映射目标——那会把源端的错误分配原样搬进 L20。应当只在**位置/方向层面**（指尖位置、骨段方向、指尖对距离）定义目标，让 L20 的 DIP 作为从变量由 mimic 决定。这一条已写入 handoff 的下一步计划。

本附录数字同样是描述性诊断：不能当作人体关节角真值，也不能证明 L20 上哪种耦合补偿更好。
